# How We Compare Routes Fairly

Comparing routes is useful only when the comparison itself is fair.

Two routes should not be judged from isolated results taken under different conditions.

## Keep The Test Conditions Comparable

When possible, we try to keep the important conditions the same.

Examples include:

- The same device
- The same local network
- The same destination
- The same application or game
- Similar testing times
- Similar traffic conditions

Changing too many variables at once makes the result harder to interpret.

## Compare More Than One Measurement

A single ping result does not tell the full story.

We may compare:

- Average latency
- Latency variation
- Packet loss
- Route consistency
- Peak-hour behaviour
- Repeated test results

The goal is to understand how each route behaves over time, not only which one produces the lowest number once.

## Avoid Unfair Comparisons

A route tested during a quiet period should not be directly compared with another route tested during congestion.

Likewise, results from different local networks or different server regions may reflect factors outside the route itself.

When the conditions are not comparable, we treat the result carefully instead of forcing a conclusion.

## Look For Repeatable Differences

A useful difference should appear consistently enough to be reproduced.

If one route performs better only once, that may be temporary.

If the same advantage appears across repeated tests under similar conditions, the difference becomes more meaningful.

## Judge The Whole Connection

We do not compare routes only by asking which one is faster.

We also consider whether the route is:

- Stable
- Predictable
- Consistent over time
- Suitable for the actual use case

A slightly slower route may still be the better route if it behaves more reliably.

## Fair Comparison Before Recommendation

Route comparisons should reduce uncertainty, not create a misleading impression.

Before recommending one route over another, we try to make sure the observed difference comes from the route itself rather than from unrelated testing conditions.
